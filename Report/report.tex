\section{Introduction}
% Context, motivation, system under test, and objective of this experiment.

% =====================================================

The goal of this project is to analyze the performance of SIMD Instructions and how their performance is affected by
the datasize, size of the vector, memory alignment, data size, and compiler optimization.

To do this I will run multiple experiments across three different kernels:

\begin{enumerate}
	\item Vector Multiply and Accumulate: $\vec{y} = a \times \vec{x} + \vec{y} $
	\item Vector Elementwise Multiplication: $z_i = x_i * y_i$
	\item 3-Element 1D Stencil: $y_i = a\times x_{i-1} + b \times x_{i} + c \times x_{i+1}$
\end{enumerate}

For each kernel I will adjust the size of the vector using different vectoriziation instructions (SSE, AVX, AVX512).
Adjust memory alignment, element size (FP32 vs FP64), number of elements provided, and compiler flags for
autovectorization.

Performance will be evaluated using the Linux \texttt{timespec} to measure execution time of the vector execution while
isolating overhead from I/O operations, and verification.

\begin{hypothesisbox}
	\textbf{Hypothesis:} \\
	% State the falsifiable prediction before running anything.

	Shifting the memory alignment off of the 64 Byte alignment that is preferred by AVX512 will significantly affect the
	performance of the SIMD instructions. The instructions will likely still run, however they will not run efficiently and
	may even be slower than the scalar counterpart.

	\textbf{Reasoning:} \\
	% Why do you expect this outcome? Reference architecture, prior results, theory.

	a time. If the memory is shifted off the memory alignment boundary it will have to do multiple data fetches to fill the

\subsection{Verifying Correctness}

To verify correctness of the serial kernels I apply standard formal verification techniques. The kernels are each short
enough where formal verification techniques of establishing preconditions and determining the resulting postconditions
are sufficient to prove correctness of the kernel.

\subsubsection{SAXPY}
\begin{ccode}[caption={SAXPY kernel (C)}, label={lst:c-example}]
	// Precondition: a, x, y are each arrays of `len' number of T elements
	// Precondition: Type T is either a float or double
	KERNEL_INLINE void saxpy_impl_##SUFFIX(const T *restrict a,
	const T *restrict x, T *restrict y,
	size_t len, size_t stride) 																								{

			for (size_t i = 0; i < len; i++) // Loop Terminates since len is a finite integer

			y[i * stride] += a[i * stride] * x[i * stride];

		} // Postcondition: y[i * stride ] = a[i * stride] * x[i * stride] + y[i * stride] for all i < len
\end{ccode}

\subsubsection{Vector Multiply}

\begin{ccode}[caption={Vector Elementwise Multiplication kernel (C)}, label={lst:c-example}]
	// Precondition: x, y, z are each arrays of `len' number of T elements
	// Precondition: Type T is either a float or double
	KERNEL_INLINE void multiply_impl_##SUFFIX(const T *restrict x,
	const T *restrict y,
	T *restrict z, size_t len,
	size_t stride) {
			for (size_t i = 0; i < len; i++) // Loop Terminates since len is a finite integer

			z[i * stride] = x[i * stride] * y[i * stride];

		}
	// Postcondition: z[i * stride ] = x[i * stride] *  y[i * stride] for all i < len
\end{ccode}

\subsubsection{Three Stencil}

\begin{ccode}[caption={Three Element Stencil Kernel (C)}, label={lst:c-example}]
	// Precondition: x, y are each arrays of `len' number of T elements
	// Precondition: Type T is either a float or double
	KERNEL_INLINE void stencil_impl_##SUFFIX(const T *restrict x, T *restrict y,
	T a, T b, T c, size_t len,
	size_t stride) {
			for (size_t i = 1; i < len - 1; i++) // Loop Terminates since len is a finite integer

			y[i * stride] = a * x[(i - 1) * stride] + b * x[i * stride] + c * x[(i + 1) * stride];

		}

	// Postcondition: y[i * stride] = a * x[(i - 1) * stride] + b * x[i * stride] + c * x[(i + 1) * stride]; for all i < len
\end{ccode}

\section{Measurement Discipline}

\subsection{Experimental Setup}
\begin{itemize}[leftmargin=1.5em]
	\item \textbf{Hardware:} CPU: x86\_64 AMD Ryzen AI 7 350 w/ Radeon 860M (SIMD Support: SSE, SSE2, AVX, AVX2, AVX-512), Memory: 32GB LPDDR5 @ 5600MT/s
	\item \textbf{OS / Kernel:} Pop\_OS! 24.04 Running Linux 7.0.11-76070011-generic
	\item \textbf{Compiler \& Flags:} GCC 16.2.0, Flags: -O2 -march=znver4 -ftree-vectorize (disabled for serial experiments)
	\item \textbf{Isolation techniques:} Ran on CPU2 with 100\% affinity, and -20 niceness (ensure no context switching)
	\item \textbf{Trials per condition:} The kernels were run in a loop for 100ms and then run 30 times then reporting the median execution time.
	\item \textbf{Timer / Instrumentation:} clock\_gettime(CLOCK\_MONOTONIC)
	\item \textbf{CPU Governor:} The CPU Governor was set to `Performance Mode' on all core with a maximum frequency of 2000MHz
\end{itemize}

\subsection{Statistical Treatment}

To ensure that the AVX execution units are warmed up and able to run at their fastest clock. To achieve this, the
kernels are run in loops for 100ms without recording performance data before running the measured runs. Then to avoid
variation from different processes running on the computer, the kernels are ran 30 times, measuring the performance on
each run. Then the median execution time is reported and used in the plots and charts.

\section{Negative / Failure Case}

\begin{failurebox}
	\textbf{What failed:} \\
	Loops that contain data that is strided did not see any benefit from SIMD vectoriziation. I expected that strided data would be slower
	than packed data but that SIMD would still provide some speedup. However, in most cases the strided data completely eliminated any
	speedup from using SIMD. For my handwritten AVX512 code, it was significantly slower than the serial execution.

	\textbf{Evidence:} \\
	Figure \ref{fig:data-stride} shows that as soon as data stride exceeds the unit stride, that the performance benefits from vectoriziation disappear
	or reverse making serial execution faster.

	\textbf{Root cause (if known):} \\
	In my handwritten AVX512 implementation, I use `VGATHER' and `VSCATTER' which can each take upto 13 or 17 cycles resepectively. Whereas the alligned load
	only takes 1 cycle and the Fused-Multiply-Add operation also only takes 1 cycle. Gathering and scattering data across strided regions of memory ends up
	taking most the execution time.

\end{failurebox}

\section{Honest Anomalies}

\begin{anomalybox}
	% Report unexplained results honestly, even if they don't fit the narrative.
	% Include: what was observed, what was expected instead, and what was (or wasn't) ruled out.

	\textbf{Anomaly 1:} \\

	As shown in figure \ref{fig:bandwidth} the bandwidth falls off a cliff when the working set size becomes greater than
	$2^{15}$ elements. Then picks back up as the number of elements grows to $2^{19}$ elements. This would imply that L3
	cache is faster than L2 cache, which is not correct. The exact reason for this is unknown because very few things were
	running on the other cores.

	\textbf{Anomaly 2:} \\

	When changing the number of tail elements to process, as indicated by figure \ref{fig:tail-elements} both the serial
	and the vectorized execution time changed. I wouldn't expect that the serial execution time would change with the
	number of tail elements.

\end{anomalybox}

\section{Discussion}
% Tie hypothesis, validation, results, and anomalies together. Was the hypothesis supported,
% refuted, or inconclusive? What would you do differently next time?

Overall my hypotheses held up pretty well. Vectoriziation did introduce a significant speedup, the specific speedup did
depend on the data alignment, tailing element size, and working set size. For small working sets, my prediction for
speed was somewhat correct, creating speed-ups of around 5x for FP32, whereas I predicted a much greater speedup. My
handwritten AVX512 code was not that much faster than what the compiler could create, and in certain cases like strided
data significantly slower than even serial execution.

My hypothesis regarding data alignment was also mostly correct, data alignment does have a significant impact on the
performance of vectorized code, the actual impact though is less predictable than I would have thought and the
vectorized execution is more resilient to misaligned data than I thought it would be.

% =====================================================
\section{Conclusion}

Overall, vectoriziation is a very strong potential compiler optimization for data that is contiguous in memory and is
aligned to the 64 byte cache line. Although my handwritten AVX512 vectoriziation was slightly faster than the compiler
in certain circumtstances, the compliler produced vectorized code that better handled more general cases. The compiler
also didn't spend an entire day trying to write AVX512 code. For this reason, programmers should focus on designing
data structures and functions that keep data in contiguous memory and give the compiler as many opportunities to
automatically vectorize the code.
